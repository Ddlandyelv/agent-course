六块积木，模型只占一块

做个 Agent 不是「调个模型」，是搭一套装置。这一页用一张图和一个小王助理，把六块积木逐个对上号。

6 分钟 零基础 含结构图
这一页在能力栈上的位置
对应环节结构层 · 组成部件
不学卡在哪以为换个更强的模型就能解决问题，忽略了外面那五块。
它解决什么把「一个 Agent」拆成可分别实现、分别排查的六块。

1模型只占中间那一小块

很多人以为做个 Agent 就是「调个模型」。其实模型只占中间那一块，其余全是你要搭的。

角色设定你是谁、规矩是什么
→
记忆刚才聊了啥、以前做过啥
→
大模型只读文字、只写文字
→
工具查资料、算数、发消息
→
回填把查到的再喂回去
这一块放在哪谁负责
角色设定（Profile）系统提示词的最前面你写
记忆（Memory）每次请求前拼进上下文你的程序
大模型（LLM）一次 API 调用供应商
工具（Tools）工具描述 + 你的执行函数你写
结果回填（Observation）追加到对话记录你的程序

六块里只有「大模型」是租的，其余五块都是你亲手搭的。这也解释了为什么同一个模型，不同产品用起来差别巨大。

2想象你请了个助理，叫小王

上面每一块都能对应到小王身上，对着看一遍就记住了：

大模型 = 他的脑子租来的

读得懂话、想得明白、写得出像样的回复。但有个死穴：他只会读写文字，没有手。

你说「帮我把文件发出去」，他能写一句「好的，我这就发」，文件还在原地没动。

角色设定 = 给他的岗位说明你写

「你是画室助教，只答课程相关的问题，学生隐私不能透露。」决定了他的口吻和守不守规矩。

岗位说明写歪了，后面全是歪的——这一块改起来最便宜，影响最大。

记忆 = 他的工作笔记你搭

短期的是「刚才聊到哪了」，长期的是「上个月那个问题后来怎么解决的」。

为什么要分开？因为模型本身记不住——每次对话对它都是初次见面，所谓「它记得我说过的话」，是你每次把记录重新贴给它看。

工具 = 他的手你接

查天气、搜网页、读文件、发邮件。每个工具本质就是一个小程序，模型自己按不动，只能「说」自己按哪个。

结果回填 = 把看到的告诉他你写

工具跑完拿到「明天小雨」，要重新塞回去，他才知道下一步该干嘛。少了这步，他就永远停在「我派人去查了」。

3为什么要拆成六块看

因为拆开之后，「出错」这件事第一次可以被定位。同一个坏结果，可能是五种原因之一：

现象先说哪一块坏了怎么验证
答得很礼貌但答偏了角色设定把岗位说明改严一句，重跑同一题
同一个坑反复摔记忆把上次的结论手动贴进上下文，看是否还犯
说要查但没查工具描述 / harness打印模型原始返回，看有没有发出工具调用
查了却当成没查结果回填看回填的格式是不是它读得懂的
看起来像在乱想模型本身换成规则更清晰的提示，看是否还乱

如果不拆，你只会说「Agent 不行」。拆开之后，你能说出「是回填格式让它误解了」，改一行就好。

本页要点

  1. 一个 Agent 六块：角色设定、记忆、模型、工具、结果回填。模型只占一块。
  2. 小王助理的比喻可以逐块对上，记不住结构时回想他。
  3. 拆成六块的价值在于能定位错误，而不是笼统地说「模型不行」。

★自测

Q1模型说「我这就去发文件」，文件却没动。最可能坏在哪？
这是「没有手」的典型表现。模型能描述动作，但动作得由你的程序执行，执行结果还得喂回去。
Q2Agent 反复犯同一个错，优先怀疑哪一块？
「反复」这个词指向记忆。验证方法很简单：把上次的经验手动贴进上下文，看它还犯不犯。
