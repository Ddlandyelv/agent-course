1缺什么：它没有手

模型能写「我帮你查一下」，但它查不了。工具调用要解决的就是这一层：让模型说出「我要用哪个工具、参数是什么」，由外面的程序去执行。

这件事听起来像工程细节，其实是一篇论文开的头。

2Toolformer：让它自己试出「调用之后更有用」

2023 年 2 月，Meta 的 Schick 等人换了个思路：不用人教它怎么用工具，让它自己试。

  1. 让模型自己生成一堆候选的 API 调用（查计算器、查维基、翻译、查日历）。
  2. 真的执行这些调用，比较「加了这个调用」和「不加」时，预测下一个词的效果好坏。
  3. 变好就保留这条样本，用来自我微调。

等于用「调用之后更会预测」当老师。关键数字：只用少量示例做自监督，在计算器、问答、翻译、日历等任务上超过同规模的 GPT-3，同时没有损害它的语言能力。

局限也很明确：它只学得会「有明确数值收益」的调用；需要串好几步才能见效的复杂工具链，这种信号太弱，学不到。

3工程上真正要写的是三样

要写什么写不好会怎样一条经验
工具名 + 一句话说明模型不知道什么时候该用它，或者到处乱用说明里写「什么时候用」，不只写「它是什么」
参数 schema参数缺字段、类型错、传了不存在的枚举值枚举写全，必填项标清，能给默认值就给
返回值太长挤爆上下文，或格式它读不懂结构化、截断、错误也返回结构化

经验之谈：工具描述是给模型看的提示词，不是给人看的文档。同一段代码，把描述从「查询天气」改成「当用户问今天/明天/未来几天的天气、温度、是否下雨时使用，参数 city 用中文城市名」，调用准确率会明显不同。

工具不是越多越好。每多一个工具，模型就多一个选错的机会。超过 10 个工具时，先分组或加一层「先选类别再选工具」。

4工具调用与「工作流」的分界

同样是调接口，两种情况完全不同：

谁决定调哪个例子
工作流里的调用你的代码。到第几步就调第几个先把文档切块 → 向量化 → 检索 → 拼进提示词
Agent 里的调用模型。它看当前情况自己挑同样的任务，它先判断「要不要先查一下术语」

这也是 0.2 那页的判断标准落到实现层的样子：工具由谁挑，决定了它是工作流还是 Agent。

本页要点

  1. 工具调用解决「没有手」：模型说调哪个，程序去执行。
  2. Toolformer 用「调用后是否更会预测」当信号，让模型自学何时调工具。
  3. 工程上真正要写的是工具名与用途说明、参数 schema、结构化返回值。
  4. 工具由代码挑是工作流，由模型挑才是 Agent。

★自测

Q1Toolformer 用什么当「该不该保留这个调用」的信号？
这就是它的巧妙处：不需要人标注「这个调用对不对」，用语言模型自己的目标（预测下一个词）当老师。
Q2工具描述应该怎么写？
工具描述本质是提示词。写清「何时使用」比写清「它是什么」对准确率影响更大。
