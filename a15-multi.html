1一句话背后的那张网

现在用大模型的方式，基本是「一次一问、一次一答」：你说一句，它回一段。这个模式高效、直接，但它只适用于定义清晰的单一任务——写一段文案、解释一个概念、翻译一句话。

现实里的目标很少长这样。以「计划一次五天四夜的三亚家庭旅行」为例，这句话背后是一张网：

  • 先看预算——口袋里有 1.5 万，能去哪、住什么档次
  • 查天气——十二月三亚是否下雨，要不要带伞
  • 查航班和酒店——哪个时间段便宜，哪个位置方便
  • 发现订不到——「这周五晚上没有空房了」，得改酒店
  • 改完再看路线——换的酒店离景点远了，行程要重排
  • 最后打包行李

2三个特征，恰好是一次一问做不到的

特征为什么一次一问做不到
多步骤每一步的输入依赖上一步的结果。查完预算才知道能住什么档次，不是并列关系
要动手查航班、订酒店、比价，都需要真的调接口，光会说没用
会反复「这周五没房」是一个意外，需要回头改方案。单轮对话没有「回头」这个动作

所以 Agent 要解决的不是「答得更好」，而是「把一串动作串起来，并且在中间出错时能改」。

这也是为什么它的核心不是模型更强，而是多了记忆、规划和工具这三样东西。

3一个 Agent 就够了吗

同样这件旅行的事，一个 Agent 也能做，只要它的上下文撑得住、工具接得全。真正逼你拆成多个的，是三件事：

逼你拆的原因表现拆了之后
上下文塞不下同时要记住预算、天气、航班、酒店、路线，很快爆窗每个角色只管自己那摊信息
技能冲突一个提示里既要「严格核算」又要「灵活推荐」，两套口径互相打架不同角色用不同提示，各守一套标准
需要独立审核自己写自己查，查不出盲区审核员另开一个上下文，只看结果

注意：这三条都是信息与判断的结构问题，不是「任务太大」。任务大但信息能装下、判断能自洽的，一个 Agent 反而更稳。

4拆之前先问一句

「这件事如果由一个人做完，他需要同时记住多少东西、同时守几套标准？」
答案是「不多」——那就别拆。拆开带来的通信成本，通常比你想的高（见 13 页）。

本页要点

  1. 真实任务有三个特征：多步骤、要动手、会反复，单轮问答都做不到。
  2. Agent 解决的不是答得更好，是把动作串起来并在出错时改。
  3. 逼你拆成多个角色的，是上下文塞不下、技能冲突、需要独立审核——不是「任务大」。

★自测

Q1「这周五没房了」这个意外，为什么单轮对话处理不了？
一次一问的形态是线性的：问完就结束。要回头，必须有循环和状态。
Q2下面哪个理由不足以支撑拆成多个 Agent？
「大」不是理由。信息装得下、判断能自洽，一个 Agent 更稳；拆开要付通信成本。
